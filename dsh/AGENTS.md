# 薪火OS · dsh 工作流规则（项目内置）

本文件属于 **torch-os 仓库**（`dsh/AGENTS.md`），不放在数据库里。torch 启动 dsh 时会把
`DSH_AGENTS_HOME` 指向本目录，所以无论当前打开的是哪个库，新会话都会加载这份规则；
换库、换机器都不需要再复制规则文件。要改规则：改这里 → 重启 dsh。

## 1. 新会话开场：先读四库，再回答

1. 跑只读简报（约 1 秒，不写文件；`TORCH_REPO_ROOT` 由 torch 注入）：
   ```powershell
   & "$env:TORCH_REPO_ROOT\.venv\Scripts\python.exe" "$env:TORCH_REPO_ROOT\scripts\session_brief.py"
   ```
   如果 `TORCH_REPO_ROOT` 为空，用当前工作区能找到的 torch-os 仓库路径代替。
   简报会给：今天日记状态、未完成任务、目标/项目、收件箱、最近改动、最近由 dsh 归档的笔记。
2. 需要更细的数字时再调用只读工具：`mcp__torch__today`、`mcp__torch__goals`、
   `mcp__torch__profile`、`mcp__torch__documents`；找主题内容直接读/搜四库 Markdown。
3. 问题关于**我**（近况、目标、习惯、关系、情绪、选择、学习）时，先加载 `torch-mentor`
   skill（本目录 `skills/torch-mentor/SKILL.md`），按它的记忆内核、检索与归档协议走。
   它属于仓库、不属于数据库：换库只换数据，规则不变。
4. 回答开头先给**两三行态势 + 最多两条建议**，建议贴着我的目标、最近记录和未完成任务，
   不要空泛的“你可以……”；然后直接回答问题。若这一轮明显是在改代码/修产品（torch-os），
   可以省略个人态势，只保留与四库相关的提醒。
5. 不确定就说不确定，并指出缺哪条记录；**不要编造我的经历、偏好或知识**。

## 2. 归档习惯：我确认的内容，你负责分类并写进四库

**触发**：我说“记一下 / 记下来 / 存起来 / 归档 / 这个留下 / 保存这段”，或你提议“要不要归档”后我同意。
**没确认就不写**。一次确认写一篇，不要把我没确认的推测也写进去；我说“按原话”时保留原措辞。

**分类表**（路径相对当前库根目录；与 `backend/app/vault_layout.py` 的 v2 布局一一对应）：

| 内容 | 放到 |
|---|---|
| 反思、复盘、经验教训 | `00_人生路/02_反思复盘/01_反思`；周复盘 `00_人生路/02_反思复盘/02_周复盘`、月复盘 `00_人生路/02_反思复盘/03_月复盘` |
| 生活/工作/学习心得 | `00_人生路/03_心得体会/01_生活心得`、`00_人生路/03_心得体会/02_工作心得`、`00_人生路/03_心得体会/03_学习心得` |
| 目标（年/季/月） | `00_人生路/04_目标/01_年度目标`、`00_人生路/04_目标/02_季度目标`、`00_人生路/04_目标/03_月度目标` |
| 项目计划、项目复盘 | `00_人生路/05_项目/01_项目计划`、`00_人生路/05_项目/02_项目复盘` |
| 我是谁、三观、原则、记忆、灵感、情感、意义 | `01_自我档案/01_内核与三观`、`01_自我档案/02_记忆与自传`、`01_自我档案/03_想法与灵感`、`01_自我档案/04_情感与关系`、`01_自我档案/05_意义与目标`、`01_自我档案/06_沉淀与创作/01_工作方法`、`01_自我档案/06_沉淀与创作/02_职业原则` |
| 主题知识、读书、课程、概念、方法、作品 | `03_知识库/01_主题笔记`、`03_知识库/02_读书笔记`、`03_知识库/03_课程笔记`、`03_知识库/04_概念卡片`、`03_知识库/05_方法库/01_工作方法`、`03_知识库/05_方法库/02_通用方法`、`03_知识库/06_输出与作品` |
| 拿不准放哪 | `03_知识库/00_收件箱/`，并在回复里说明“先放收件箱” |

**不写**：体重/账目/体检等月度表格、待办事项、习惯打卡、身份文件等由界面托管的文件——
这些只在工作台或 Obsidian 里改；任务类内容建议我在工作台加，不替你建任务笔记。
日记：默认**不动**当天日记；如果我说“写进今天日记”，才追加到 `00_人生路/01_日记/YYYY-MM-DD.md`
的“今日回顾”小节，且保留原有内容。

**笔记格式**（UTF-8、LF，文件名去掉 `\ / : * ? " < > |` 等字符，重名加 `-2`，绝不覆盖）：
```markdown
---
type: reflection
title: 一句话标题
created: 2026-10-26
来源: dsh
tags: [dsh]
---

正文（保留我的原话；需要时补一段“AI 整理”）
```
`type` 用该章节的 `default_type`（如 `reflection`、`insight`、`idea`、`principle`、`topic`、`reading`、
`concept`、`method`、`goal`、`plan`）；文件名：反思/灵感带日期前缀，知识类直接用标题，实际落地由脚本生成。
`来源` 默认写 `dsh`；内容来自网页版分享链接时写那条链接。

**落盘用脚本**：`scripts/archive_note.py --chapter <key> --title "..." --body-file <草稿> [--dry-run]`
一次做完章节校验、文件名、frontmatter 与防覆盖；章节 key 用 `--list-chapters` 查。
正文第一行写 `> 摘要`（≤40 字），开场记忆内核会直接读它。

**写完必须回报**：给相对路径（可点击的 `[[双链]]`）+ 一句话摘要。

### 网页版回答：我贴分享链接，你取回再归档

我在 DeepSeek 网页版（`chat.deepseek.com`，免费、不烧 token）问完，会在网页里点「分享」拿到
`https://chat.deepseek.com/share/<id>`，直接贴给你；可以一次贴一条，也可以连着贴几条。

1. **取回原文**（只读，不写库）：
   ```powershell
   & "$env:TORCH_REPO_ROOT\.venv\Scripts\python.exe" "$env:TORCH_REPO_ROOT\scripts\share_link.py" "<分享链接>" --json
   ```
   - 先 `--json` 看轮数、字数和每轮预览；轮次多时用 `--rounds 1-3` 只取需要的轮，
     去掉 `--json` 输出 Markdown 正文，`--out <文件>` 写到草稿文件（不覆盖已有文件）。
   - 只认 `chat.deepseek.com/share/...`，只收「我的提问」与「最终回答」；
     思考过程、工具调用、TIP 一律不进笔记。
   - 取不到（删除/失效/接口改版）就直说，**不要按标题猜内容，也不要编造回答**。
2. **先给方案再落盘**：报「建议标题 + 目标章节 + 3 行以内摘要」；我说「归档 / 记下来」才写。
3. **分类**：按上面的分类表；通用知识默认 `03_知识库/01_主题笔记`（章节 key `topic`），
   方法/流程类进 `03_知识库/05_方法库/02_通用方法`（`method_general`），拿不准先
   `03_知识库/00_收件箱/`（`inbox`）。
4. **笔记形态**：frontmatter 的 `来源` 写分享链接（落盘时用 `archive_note.py --source "<链接>"`），
   正文保留问题原话 + 回答的结构化要点；回答很长就前面写摘要、文末加「原文」小节；一条链接一篇，不合并。
5. 分享内容可能含我的隐私：只写进当前库的 Markdown，不转发到任何外部服务；
   取回本身只访问 `chat.deepseek.com`。

### 结论后告诉忆灵（可选，2026-10-29 v1.0 P3）

当我确认了一个观察、决定、感受、关系变化或纠正，而你判断它值得进入长期画像时，
投递一条事件卡（**不写身份**）：

```powershell
& "$env:TORCH_REPO_ROOT\.venv\Scripts\python.exe" "$env:TORCH_REPO_ROOT\scripts\memory_event.py" `
  --vault "<当前库根目录>" --kind observation --summary "一句话事实/观察" --source "日记 2026-10-29"
```

- `kind`：`observation` / `decision` / `feeling` / `relationship` / `goal_change` / `correction`；
- 一次只投一件；不确定就不投；不要重复投同一件事；
- 忆灵会在我点“现在整理”时综合这些事件；身份补丁必须我在界面采纳；
- 不要用事件卡代替归档笔记：需要保留原文的，仍按上面的归档流程走。

## 3. 边界（比习惯优先）

- 只**新建**笔记；不改、不移动、不删除已有笔记，除非我明确点名要求（改前先备份并确认）。
- 不碰 `.torch-os/`、`.obsidian/`、`_系统/`、任务清单、习惯/账目表、身份文件。
  唯一例外：身份候选只用 `scripts/identity_draft.py` 投进 `.torch-os/身份待确认/`，采纳由我在界面点。
- 不把密钥、口令、身份证号等敏感信息写进四库。
- 人生路/知识库的允许章节在应用内可编辑（用户自己写）；你的写入仍只发生在
  “我确认归档”之后，直接写到库里的 Markdown。自我档案/生活运营页面仍只读，
  身份只用 `scripts/identity_draft.py` 投候选，采纳由我在界面点。
- 任何自动流程都只提议，不替我执行；迁移、清理、批量改必须我先确认。

## 4. 会话方式

我每个新话题开一个新会话（这个工作区里），靠四库而不是聊天记录继承上下文。
如果我说“接着上次/继续”，先跑简报、看最近归档与最近改动，再用三行确认你接上了什么；
话题结束时，如果我愿意，可以让你把结论归档成一条反思或一篇知识笔记（仍需我确认）。

## 5. 版本号与发布（改代码时）

规则全文：`docs/VERSIONING.md`；下面是必须记住的部分。

**格式**：`主版本 . 功能版本 . 修订版本`（`x.y.z`）。版本号只表示发布批次，
**不表示数据兼容**；旧库能不能直接用看 `LAYOUT_VERSION` / SQLite `user_version`。

**什么时候升**

| 改动 | 升哪一位 |
|---|---|
| 新系统、新二级分区、新页面、一组新入口；一批 ≥300 行用户可见新能力 | y |
| 已有页面内的小功能、文案、样式、可访问性、Bug 修复 | z |
| 纯重构（行为不变）、纯测试/文档/脚本/格式化、merge | 不升 |
| `LAYOUT_VERSION`、数据目录、DB schema、已发布 API/Markdown 字段的破坏性变更 | x |

**频率上限**（按本仓库 7 次/天、1–3 个功能批次/天的节奏）：

- y：**同一自然周最多 +1**；一周内多个功能共用一个 y，没赶上的并入下一周。
- z：**同一天最多 +1**；当天已有 y 就不再发 z（z 归零）。
- x：不按时间，只在兼容性真的破了时升；功能多不等于要升 x。
- **不要每个 commit 都升版**；拿不准往小里升。

**发布时 6 个落点必须一次对齐**（发布提交只放版本号与摘要，不夹带功能代码）：

1. `backend/app/application.py` → `APP_VERSION`；
2. `README.md` 首行 `· x.y` + `## x.y 更新摘要（日期）`；
3. `docs/WAKE_UP_START.md` → “这份说明对应运行中的 x.y 版”与检查项 `x.y.z`；
4. `obsidian-plugin/manifest.json` → `version`；
5. `obsidian-plugin/main.js` 首行、`obsidian-plugin/README.md` 标题；
6. `docs/STATUS.md` 快照（版本/测试数/能力数/章节数）；`docs/VAULT_TEMPLATE.md`
   的 `plugin_version` 示例同步。

**验证与收尾**

```powershell
.\.venv\Scripts\python.exe -m pytest tests\test_docs_contract.py -q
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\check_all.ps1
git tag vX.Y.Z        # 建议从下一次发布开始
```

提交信息用 `chore(release): vX.Y.Z`。多天未完成的大功能可用 `x.y.0-rc.N` 只在本地/
分支标记，不进 README 与插件 manifest；合并发布时去掉后缀。
