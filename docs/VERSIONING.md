# 版本号与发布规则（2026-10-31 制定）

> 这份规则回答一件事：**什么时候把 `APP_VERSION` 往上加，加哪一位。**
> 它按这个仓库真实的提交节奏设计，不按「每次 commit 都升版」的教科书流程。

## 1. 先看清楚这个仓库的节奏

2026-10-15 到 2026-10-31（17 天）：

- **123 次提交，平均约 7 次/天**；多数活跃日 5–18 次，10-22 一天 34 次；
- 功能不是均匀落地的，而是**一天 1–3 个大批次**：
  健康系统 116 个文件 / +8,980 行，dsh 集成 108 / +11,876，AI 角色层 91 / +10,091，
  恋爱系统 20 / +5,229，写作空间 24 / +2,398，任务目录重构 51 / +2,357；
- 修复提交通常只有 2–50 行，一天可能连着好几个；
- `1.0.0` 是 2026-10-30 在 P0–P5 收口时发布的一次里程碑，不是每个功能各发一版。

结论：**版本号对应「一次对外可感知的发布批次」，不对应 commit 数，也不对应日期。**
如果按 commit 升版，17 天就会到 1.123.0，编号立刻失去意义。

## 2. 编号格式

```text
主版本 . 功能版本 . 修订版本
  x    .    y     .    z
```

- **x（主版本）**：数据或接口**不再向后兼容**时才 +1；
- **y（功能版本）**：一次**功能批次**发布时 +1；
- **z（修订版本）**：一次**修复批次**发布时 +1。

版本号只表示「发布批次」，**不表示数据兼容性**。数据能不能直接打开，看
`LAYOUT_VERSION`（当前 `pillars-v2`）、SQLite `user_version` 与迁移/备份报告；
不要用 `APP_VERSION` 推断旧库能否直接用。

## 3. 什么时候升哪一位

| 判定 | 升 x | 升 y | 升 z | 不升 |
|---|---|---|---|---|
| 新增系统 / 二级分区 / 页面 / 一组新入口 |  | ✓ |  |  |
| 一批用户可见的新能力（≥ 约 300 行新增用户可见代码，或 ≥ 10 个文件） |  | ✓ |  |  |
| 已有页面内的小功能、文案、样式、可访问性改进 |  |  | ✓ |  |
| Bug 修复、数据订正、兼容补丁 |  |  | ✓ |  |
| 纯重构：行为不变（`refactor`） |  |  |  | ✓ |
| 纯测试 / 文档 / 脚本 / 格式化 / 临时文件 |  |  |  | ✓ |
| merge commit、回滚到上一发布状态 |  |  |  | ✓ |
| `LAYOUT_VERSION` / 数据目录 / DB schema / 已发布 API 破坏性变更 | ✓ |  |  |  |
| 删除或改名已发布的 Markdown 字段、接口，需要用户迁移 | ✓ |  |  |  |

补充：

- **功能很多不等于主版本要升。** 3 天做 5 个系统仍然可以是 `1.5.0`；只有
  「旧数据/旧客户端会坏」才配 `2.0.0`。
- **同一批工作里既有功能又有修复**：按功能升 y，修复并入该版本，不再单独升 z。
- **拿不准时往小里升**：能 z 不 y，能 y 不 x；下个批次再补。

## 4. 频率上限（按这个仓库的节奏）

| 位 | 上限 | 说明 |
|---|---|---|
| y | **同一自然周最多 +1** | 一周内多个系统/功能共用一个 y；没赶上的并入下一周。按 1–3 个功能批次/周的实际节奏，一年大约 30–50 个 y，不会失控。 |
| z | **同一天最多 +1** | 同一天多批修复合并成一个 z；有 y 的当天不再发 z（z 归零）。 |
| x | 不按时间 | 只在兼容性真的破了时升，可能几个月一次，也可能一年一次。 |

这样做的原因：你的提交是「批量落地」型，按天/按 commit 升版会制造大量无意义编号；
按周收口既能反映功能节奏，又保留 hotfix 的 z 通道。

## 5. 发布动作清单（一个版本一次做完）

版本号有 6 个落点，**必须同一次提交里全部对齐**，否则 README/运行版本会漂移：

1. `backend/app/application.py` → `APP_VERSION = 'x.y.z'`（唯一代码来源）；
2. `README.md` 首行 → `# 薪火OS（Torch OS）· x.y`（只写前两位），并在「更新摘要」补
   `## x.y 更新摘要（YYYY-MM-DD）`；
3. `docs/WAKE_UP_START.md` → 首段「这份说明对应运行中的 x.y 版」，
   启动检查里的 `version` 改成 `x.y.z`；
4. `obsidian-plugin/manifest.json` → `"version": "x.y.z"`；
5. `obsidian-plugin/main.js` 首行注释、`obsidian-plugin/README.md` 标题 → `x.y.z`；
6. `docs/STATUS.md` 快照 → `APP_VERSION`、测试数、能力数、章节数；
   `docs/VAULT_TEMPLATE.md` 的 `plugin_version` 示例随 manifest 更新（它是动态读取的展示样例）。

然后：

```powershell
# 文档契约：README 首行 / WAKE_UP_START 版本句 / 插件 manifest 与 APP_VERSION 一致
.\.venv\Scripts\python.exe -m pytest tests\test_docs_contract.py -q

# 发布前全量校验
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\check_all.ps1
```

- 发布提交只放版本号与更新摘要：`chore(release): vX.Y.Z`，**不夹带功能代码**；
- 打 tag：`git tag vX.Y.Z`（当前仓库还没有 tag，建议从下一次发布开始）；
- 功能提交仍按 `feat/fix/refactor/docs/test/chore` 写，不要求每个都改版本号。

## 6. 结合本仓库历史的例子

| 版本 | 场景 | 判定 |
|---|---|---|
| `1.0.0`（2026-10-30） | 四库重构 + AI 角色层 + 旧接口退役，需要迁移/兼容说明 | x：破坏性代际 |
| `1.1.0`（建议下一次） | 健康系统（新二级分区、5 个章节、+8,980 行）+ 同周其它功能 | y：新系统批次 |
| `1.1.1` | 健康页表单/评分的一个修复批次 | z：修复 |
| `1.2.0` | 下一周的新系统或一批新入口 | y：新功能批次 |
| `2.0.0` | 布局升到 `pillars-v3`、数据目录迁移、旧 API 删除 | x：不兼容 |

> 当前代码仍是 `1.0.0`。按本规则，**健康系统这一批应作为 `1.1.0` 发布**；
> 因为工作区里还有未提交的改动，发布动作留给下一次收口，不在这里顺手改号。

## 7. 预发布与分支

- 多天没做完的大功能可以用 `x.y.0-rc.N` 只在本地/分支上标记，**不进 README 与插件
  manifest**；合并发布时去掉后缀。
- Obsidian 插件 manifest 只认正式版本号；发布前必须同步为 `x.y.z`。
- 单人仓库不强制分支；如果同时改两套不兼容的东西，再开分支，避免 `main` 上出现
  「一半迁移、一半没迁移」的中间态。

## 8. 一句话决策

> **会不会弄坏旧数据/旧接口？会 → x；不会，但用户能看到新系统/新入口？→ y（本周没升过）；
> 都不会，只是修/文档/重构？→ z（今天没升过）或干脆不升。**
